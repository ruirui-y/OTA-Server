## 结果

### 5 万设备全部认证通过

```
服务端：连接=50000 在线=50000
模拟器：累计 创建=50000 连接=50000 认证=50000
服务端 warn/error：0 条
```

### CPU（20 秒窗口，不是 `ps` 的平均值）

| 阶段 | 服务端 | 模拟器 |
|---|---|---|
| 爬升期（连了 4.5 万时） | 0.37 核 | 0.51 核 |
| **稳态（5 万全部连满）** | **0.23 核** | **0.37 核** |

比阶段一的 0.35 核还低。原因：心跳走的是纯内存路径，数据库只在 Hello 和每分钟刷库时碰。

### 吞吐：QPS

5 万连接，心跳 5 秒一次。

| 指标 | 数值 | 怎么算的 |
|---|---|---|
| 心跳入站 | **9,975 帧/秒**（实测） | 服务端日志里的 QPS，理论值 5 万 / 5 秒 = 10,000 |
| 心跳出站（ack） | **约 9,975 条/秒** | 一来一回 |
| 总帧数 | **约 20,000 帧/秒** | 上下行相加 |
| 认证（爬升期） | 约 830 次/秒 | 5 万台在约 60 秒内完成 |
| 认证（稳态） | **≈ 0** | 缓存命中 |
| 数据库查询（稳态） | **≈ 0** | 只在缓存过期时查 |
| 数据库写入 | **1 条 UPDATE / 60 秒** | 批量刷 last_seen |

### 服务端处理耗时

统计口径：`OnMessage` 进入时打一个时间戳，整批字节处理完再打一个。量的是「服务端拿到一帧到回应写出去」的时间，不含网络。

每 5 秒取一次分位数，样本数正好等于这 5 秒收到的心跳数。

| 采样时刻 | QPS（帧/秒） | 样本 | p50 | p90 | p99 | p999 | max |
|---|---|---|---|---|---|---|---|
| 13:55:40 | 9,360 | 46,871 | 12 µs | 28 µs | 318 µs | 532 µs | 4.1 ms |
| 13:55:45 | 9,975 | 50,000 | 13 µs | 28 µs | 292 µs | 508 µs | 5.0 ms |
| 13:55:50 | 9,975 | 50,000 | 13 µs | 28 µs | 203 µs | 346 µs | 4.4 ms |
| 13:55:55 | 9,978 | 50,000 | 13 µs | 28 µs | 175 µs | 294 µs | 1.9 ms |

**p50 稳定在 12~13 微秒，p99 在 175~320 微秒。**

那几行日志的样子：

```
QPS=9975 帧/秒 (9975 次调用/秒) 样本=50000 p50=13us p90=28us p99=292us p999=508us max=5017us
```

「帧数」和「调用次数」完全相等，说明**每条消息一帧**，没有出现粘包把多条合并成一次调用。

一个观察，没有下结论：p99 是 p50 的 13 倍。猜测是一次读事件里积累了多帧、
`OnMessage` 循环处理多条，或者 tick 定时器和消息处理撞在同一轮。没验证过。

### 模拟器不测延迟

模拟器只负责压流量（建连、认证、发心跳），不记录往返时间。

早期在模拟器里量过，得到 p50 = 4.5 秒这种数字，是假的：4 个线程各管 12500 台设备，
心跳定时器到点是一个 `for` 循环连发 12500 个帧，发完才回到 epoll 处理 ack，
所以第 1 台设备的 ack 要等后面 12499 个帧发完才被读到。
**量出来的是模拟器自己发批次的排队时间，不是服务端延迟。**

这段采样已经删掉。**延迟一律以服务端日志里的「处理耗时」为准。**
### 缓存命中：重连时一次库都不查

用 `pg_stat_database.tup_fetched` 量。**只有 SELECT 会把它推高**，UPDATE 的扫描走 `tup_returned`，不影响这个值。

先测出噪声底：**每开一次 `psql` 连接固定 +120**（连接建立时的系统表查询）。

| 阶段 | 原始增量 | 减掉噪声 | 真实 SELECT |
|---|---|---|---|
| 首次认证 100 台（缓存空） | +272 | −120 | **152 条** |
| 断线重连 100 台（缓存命中） | +120 | −120 | **0 条** |

重连时的增量正好等于噪声底，说明**一台设备都没查库**。

### 数据库不可用时拒绝新设备

把 `--db-port` 指到 5999（连不上），起 5 台设备：

```
[warning] 数据库不可用，拒绝新设备认证, sn=sim-000000
[warning] 数据库不可用，拒绝新设备认证, sn=sim-000001
...（5 台全部被拒）
```

设备会不断重连重试，但每次都被拒，在线数始终是 0。

### last_seen 批量刷库

```
已刷 last_seen: 48325
最新一台时间:   2026-11-11 11:20:26
```

48325 而不是 50000，是因为**刷库每 60 秒一次**，查询时上一轮已经刷到 11:20:26，之后才连上来的那批还没轮到。再等一轮就是 5 万，不是 bug。

### 超时剔除（5 万规模）

冻住模拟器（`kill -STOP`，socket 不断、心跳不发），90 秒后：

```
本轮踢掉 9204 条超时连接
本轮踢掉 8143 条超时连接
本轮踢掉 4524 条超时连接
...
连接=0 在线=0
```

恢复模拟器（`kill -CONT`）后自动重连：

```
连接=40902 在线=28133
连接=43499 在线=37656
```

**分批踢、每批几千条，没有一次性雪崩。**

## 关键设计回顾

### 为什么数据库连接必须非阻塞

5 万台设备共用一个 IO 线程。同步执行一次 SELECT 要 0.5~5ms，这期间所有心跳回包都推迟；一次锁等待能推迟几百毫秒。

所以：连接用 `PQconnectStart` + `PQconnectPoll` 分步走，查询用 `PQsendQueryParams` 发出去就返回，结果靠 socket 可读事件驱动。

### 为什么用 Pipeline

```
普通一问一答：发 1 条 → 等结果 → 发第 2 条 → 等结果   一轮 10 个请求 = 10 次往返
Pipeline      ：发 10 条（只写缓冲）→ 1 个 Sync + 1 次 flush → 10 份结果一起回来
```

批边界用 `QueueInLoop`：本轮事件处理里第一个请求排一次队，这一轮后来的请求自动进同一批。

### 为什么分四条连接

一个同步点之间的 SQL 属于同一个隐式事务。一条 UPDATE 失败会把同批的 SELECT 一起判成回滚。按类型分开之后，写失败不牵连读，某条连接断了也只影响那一类。

服务端代价是四个 backend 进程（PostgreSQL 一连接一进程），每个约 3~5MB，可以忽略。

### 为什么缓存不放进会话

会话跟着连接生灭，缓存必须跨连接存活。放会话里等于每次重连都要查库，缓存就白做了。

## 边界与未测

| 项 | 说明 |
|---|---|
| 认证 QPS | 只在设备首次上线和缓存过期时查库，稳态下接近 0 |
| 5.5 万仍是天花板 | 单机单 IP 的临时端口只有 55,536 个 |
| 未测：库中途重启 | 只测了「一开始就连不上」，没测「跑着跑着断了再恢复」 |
| 未测：真跨机延迟 | 全部是本机回环，RTT 可以忽略，Pipeline 的优势体现不出来 |

## 复现

```bash
# 1. 建库建表（DBeaver 或 psql 都行）
psql -h 127.0.0.1 -U dev -d ota_server -f server/storage/sql/001_init.sql

# 2. 造 5 万台测试设备，sn 和 token 有规律
psql -h 127.0.0.1 -U dev -d ota_server -f scripts/seed_devices.sql

# 3. 起服务端
./build/linux-debug/bin/ota_server --listen 9500 --io 1

# 4. 起模拟器（--duration 到点自己退出，不给就一直跑）
./build/linux-debug/bin/ota_simulator --host 127.0.0.1 --port 9500 \
    --count 50000 --threads 4 --interval 5 --duration 120

# 5. 量 CPU（窗口测量，不是 ps 平均值）
./scripts/cpu_of.sh $(pgrep -x ota_server) 20

# 6. 看服务端处理耗时（每 5 秒一行，在服务端日志里）
grep '处理耗时' logs/server.log | tail -5
```
