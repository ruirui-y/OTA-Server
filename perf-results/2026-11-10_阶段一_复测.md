# 阶段一复测：网关长连接与心跳（链表改造后）

日期：2026-11-10
机器：VMware 虚拟机，8 核，15 GiB，Ubuntu 22.04（内核 6.8.0-138）
配置见同目录 `environment.txt`

---

## 这次为什么不看 `ps` 的 %CPU

`ps -eo pcpu` 报的是「进程启动以来的平均值」。压测刚起 30 秒时，建连那一段的尖峰全摊在里面，稳态占用被严重高估——上一版文档里「3 万连接 7.0% / 5 万连接 20%」就是这么来的，不可靠。

这次改成读 `/proc/<pid>/stat` 的 utime+stime，在指定窗口内前后各读一次相减，得到窗口内的真实占用。脚本：`scripts/cpu_of.sh`。

**表中「核」= 窗口内平均占用几个 CPU 核。0.35 就是用了三分之一核。**

---

## 结果

服务端 4 个 IO 线程，心跳间隔 5 秒（即每连接 0.2 次/秒）。

### 服务端绑 CPU 0-3、模拟器绑 CPU 4-7

| 设备数 | 在线 | 服务端(核) | 模拟器(核) | 错误 |
|---|---|---|---|---|
| 1,000 | 1,000 | 0.37 | 0.45 | 0 |
| 5,000 | 5,000 | 0.40 | 0.27 | 0 |
| 10,000 | 10,000 | 0.35 | 0.32 | 0 |
| 20,000 | 20,000 | 0.29 | 0.23 | 0 |
| 50,000 | 46,000 | 0.88 | **3.91** | 0 |

最后一行：模拟器 4 个核被打满，连接没爬完就进入测量窗口，所以只到 4.6 万。

### 服务端绑 CPU 0-1、模拟器绑 CPU 2-7

把核多分给模拟器之后：

| 设备数 | 在线 | 服务端(核) | 模拟器(核) | 错误 |
|---|---|---|---|---|
| 50,000 | **50,000** | 0.34 | 0.53 | 0 |
| 55,000 | **55,000** | 0.35 | 0.43 | 0 |

---

## 结论

1. **服务端 2 个核，处理 5.5 万长连接 + 每秒 1.1 万次心跳，只用 0.35 核。**
2. 前面三次压不上去，瓶颈都在**压测工具**那侧，不在服务端：
   - 模拟器单线程时 98% CPU，被一个核卡住
   - 每设备一个定时器时，5 万设备就是 5 万个 timer
   - 4 个核不够建连风暴，连接爬不完
3. 服务端的真实上限**还没摸到**，需要更强的压测端或第二台机器。

---

## 边界与限制

| 项 | 说明 |
|---|---|
| 5.5 万是天花板 | 单机单 IP 的临时端口范围 10000-65535，共 55,536 个，再往上需要多源 IP 或多机 |
| 服务端上限未知 | 压测端先到瓶颈 |
| 跨机未测 | 需要先对时钟 |
| 进程内存 / CPU 峰值 | 只测了稳态 CPU，没测内存峰值 |

## 复现

```bash
# 端口范围和 backlog（重启会丢，要写进 /etc/sysctl.d/）
echo -e "net.ipv4.ip_local_port_range = 10000 65535\nnet.core.somaxconn = 65535" | sudo tee /etc/sysctl.d/99-ota-bench.conf
sudo sysctl --system

# 阶梯压测（服务端 0-1，模拟器 2-7）
SERVER_CPUS=0-1 SIM_CPUS=2-7 SCALES=50000 ./scripts/bench.sh 5 20
SERVER_CPUS=0-1 SIM_CPUS=2-7 SCALES=55000 ./scripts/bench.sh 5 20

# 超时剔除验证（kill -STOP 冻住模拟器，模拟设备假死）
./scripts/test_timeout.sh 500
```

`scripts/bench.sh` 的规模由 `SCALES` 环境变量指定，心跳间隔是第一个参数，测量窗口是第二个参数。
